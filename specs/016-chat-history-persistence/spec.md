# Feature Specification: Chat History Persistence and Markdown Export

**Feature Branch**: `016-chat-history-persistence`

**Created**: 2026-11-14

**Status**: Ready for Planning

**Input**: User description: "016-chat-history-persistence (Persistent conversations & Markdown export)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Seamless Conversation Persistence Across Browser Sessions (Priority: P1)

As a user interacting with local Ollama models in e-webui, I want all my conversations, message turns, reasoning traces, timestamps, and active session selections to be automatically saved on my device and restored when I refresh or reopen the app, so that I never lose conversational context, research notes, or code generated by my local models.

**Why this priority**: Core usability foundation. Currently, any page refresh or accidental tab closure wipes all conversations and messages from memory. Persisting dialogue is essential for productive long-term local LLM usage.

**Independent Test**: Can be tested by starting a conversation, generating multiple assistant turns (including reasoning blocks and code snippets), refreshing the browser tab, and verifying that the entire session history, active conversation state, and sidebar list are restored accurately with zero data loss.

**Acceptance Scenarios**:

1. **Given** an ongoing conversation with user and assistant turns, **When** the user reloads the web page or restarts the browser, **Then** the previous conversation and its complete message history are restored and displayed within 200 ms.
2. **Given** multiple conversation sessions created across different days, **When** the application loads, **Then** all sessions appear in the sidebar correctly grouped by date category (Today, Yesterday, Previous 7 days, Older) with their custom or auto-generated titles intact.
3. **Given** a user switching between stored conversations, **When** clicking a session in the sidebar, **Then** the message list updates immediately with the selected conversation's messages and marks that session as the active session across reloads.
4. **Given** an in-flight streaming response, **When** generation completes, **Then** the finalized content, reasoning trace, model metadata, and generation metrics are immediately committed to persistent storage.

---

### User Story 2 - Export Conversation to Formatted Markdown and Structured Data (Priority: P1)

As a user who has generated useful content, code, or technical answers with a local model, I want to export any conversation as a cleanly formatted Markdown file or structured JSON file, so that I can easily archive my research, import it into external documentation tools (e.g. Obsidian, Notion, GitHub, or static site generators), or back up my dialogues.

**Why this priority**: Direct workflow value. Local LLMs are often used for private code analysis, drafting, and problem-solving; enabling one-click Markdown export makes model outputs immediately portable and shareable without tedious manual copy-pasting.

**Independent Test**: Can be tested by opening any completed conversation, clicking the Export action in the conversation menu, selecting Markdown format, and verifying that a `.md` file is downloaded containing the title, model used, timestamp, formatted dialogue turns, and intact code blocks.

**Acceptance Scenarios**:

1. **Given** an active conversation with message turns, **When** the user opens the conversation menu (via header overflow or sidebar session item) and chooses "Export", **Then** the user is presented with export options for Markdown (`.md`) and JSON (`.json`).
2. **Given** the user selects "Export as Markdown", **When** triggered, **Then** a `.md` file is downloaded with a sanitized filename based on the conversation title and date (e.g., `chat-analysis-2026-11-14.md`).
3. **Given** an exported Markdown file, **When** opened in any standard Markdown viewer, **Then** it presents a clear document structure including a title heading, export timestamp, active model name, distinct role headings (e.g., `### User`, `### Assistant`), preserved code fences with language tags, and collapsible or visually separated reasoning sections.
4. **Given** the user selects "Export as JSON", **When** triggered, **Then** a `.json` file is downloaded containing the structured data array of all session metadata, turns, reasoning, timestamps, and token metrics.
5. **Given** an empty conversation with no messages, **When** viewed, **Then** the export option is disabled or displays an informative notice that there is no content to export.

---

### User Story 3 - Session Renaming, Deletion, and Workspace Reset (Priority: P2)

As a user organizing multiple conversations, I want to rename conversations, delete obsolete threads, or wipe all historical conversations in a single action, so that I can keep my workspace organized and decluttered over time.

**Why this priority**: Essential session management. Once persistence is active, conversations accumulate; users require intuitive management controls to clean up, categorize, and securely reset their local history.

**Independent Test**: Can be tested by renaming a session title, verifying the updated title persists across refreshes and exports, deleting an individual session, and using the "Clear all chats" option in Settings with confirmation to verify complete storage cleanup.

**Acceptance Scenarios**:

1. **Given** an existing conversation, **When** the user edits the title in the header or via the sidebar menu, **Then** the updated title is saved immediately and persists across page reloads.
2. **Given** an active conversation, **When** the user clicks "Delete chat" and confirms, **Then** the conversation is permanently removed from the sidebar and persistent storage, and the app gracefully transitions to the next available conversation (or a fresh conversation if none remain).
3. **Given** the Settings modal, **When** the user navigates to the General settings tab, **Then** a "Clear all conversations" action is available with a distinct warning style.
4. **Given** the user clicks "Clear all conversations", **When** an explicit confirmation prompt is confirmed, **Then** all stored conversations and turns are permanently purged, and the UI resets to an initial empty chat screen.

---

### User Story 4 - Storage Resilience, Privacy, and Boundary Handling (Priority: P3)

As a user operating in constrained environments (such as private browsing windows, storage-limited devices, or browser profiles with strict quota policies), I want the application to handle storage boundaries gracefully without crashing, losing active work, or leaking data outside my local device, so that my offline experience remains dependable and private.

**Why this priority**: Robustness and reliability. Offline local LLM users prioritize privacy and reliability; storage quota errors or private-window restrictions must never cause unhandled exceptions or blank screens.

**Independent Test**: Can be tested by simulating storage-disabled conditions (such as incognito browsing with storage blocked) or quota-exceeded boundaries; the application alerts the user cleanly and remains completely operational in transient session mode.

**Acceptance Scenarios**:

1. **Given** a browser environment where persistent storage is blocked or quota is exhausted, **When** the application attempts to save, **Then** a non-intrusive toast notification informs the user that storage is unavailable, and all conversation features continue functioning in temporary memory without crashing.
2. **Given** corrupt or unparseable historical records in browser storage, **When** the application boots, **Then** it isolates the damaged entry, logs a warning, restores all remaining valid conversations, and prevents the app from entering a broken state.
3. **Given** multiple open browser tabs viewing the same application, **When** a new session is created or deleted in Tab A, **Then** Tab B remains stable without overwriting or corrupting shared storage state.
4. **Given** strict offline deployment requirements, **When** conversation data is saved or retrieved, **Then** 100% of data storage operations occur strictly on the client device without sending conversation logs or backups to external hosts.

---

### Edge Cases

- **Cold Start on First Visit**: What happens when a user opens the application for the very first time with empty storage? The system automatically creates a single clean default session ready for immediate prompting.
- **Concurrent Streaming and Tab Navigation**: What happens if the user closes or refreshes the tab while an assistant turn is actively streaming? The partial text received up to that moment is safely persisted with status `stopped`, avoiding half-written or corrupted state records.
- **Huge Conversation Threads**: What happens when a conversation contains hundreds of turns with massive code blocks? Persistence operations are batched or throttled so that saving does not introduce frame drops or input stuttering in the composer.
- **Special Characters in Titles for Export**: What happens when a conversation title contains illegal filename characters (e.g. `\ / : * ? " < > |`)? The export generator sanitizes the filename to safe ASCII/Unicode characters before initiating the browser download.
- **Reasoning-Only Responses**: What happens when an exported message contains only reasoning without response text? The Markdown export format explicitly presents the reasoning block so the user does not see an empty turn.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST persist all conversation sessions, message turns, reasoning contents, model identifiers, timestamps, and active session selection on the client device.
- **FR-002**: System MUST automatically restore all valid persisted conversation sessions upon application boot or page reload, defaulting to the last active session.
- **FR-003**: System MUST provide an export feature allowing users to download any conversation as a GitHub-Flavored Markdown (`.md`) file.
- **FR-004**: System MUST provide an export feature allowing users to download any conversation as a structured JSON (`.json`) file.
- **FR-005**: Exported Markdown files MUST include:
  - Document header with conversation title and export timestamp
  - Active model name and parameter metadata
  - Chronological message turns clearly distinguishing `User` and `Assistant` roles
  - Intact fenced code blocks with language identifiers
  - Collapsible or formatted reasoning blocks when reasoning content is present
- **FR-006**: System MUST persist title changes, individual session deletions, and active conversation switches immediately.
- **FR-007**: System MUST provide a "Clear all chats" option in Settings that wipes all persistent conversation data after explicit user confirmation.
- **FR-008**: System MUST perform all storage and export operations client-side, ensuring zero transmission of conversation history to external hosts or third parties.
- **FR-009**: System MUST gracefully detect storage quota exhaustion or private-browsing storage restrictions, alerting the user and falling back to in-memory operation without crashing.
- **FR-010**: System MUST automatically sanitize filenames during export to remove illegal filesystem characters while preserving readable titles.

---

### Key Entities

- **ChatSession**: Represents an individual conversation thread.
  - Attributes: Unique identifier (`id`), title string (`title`), creation timestamp (`createdAt`), last updated timestamp (`updatedAt`), associated model identifier (`model`), and an ordered collection of dialogue messages (`messages`).
- **ChatMessage**: Represents an individual turn in a dialogue.
  - Attributes: Unique identifier (`id`), session parent identifier (`sessionId`), sender role (`user` or `assistant`), text content (`content`), optional reasoning text (`reasoning`), lifecycle status (`streaming`, `completed`, `stopped`, `error`), optional performance metrics (`metrics`), and creation timestamp (`createdAt`).
- **ExportDocument**: Represents the generated export artifact for a conversation.
  - Attributes: Formatted payload (Markdown string or serialized JSON), destination filename with date stamp, and MIME type (`text/markdown` or `application/json`).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of completed messages, reasoning blocks, and conversation titles persist and accurately restore after browser refresh or browser restart.
- **SC-002**: Initial page load and session list restoration for up to 50 conversations completes in under 200 milliseconds.
- **SC-003**: Generating and initiating a download of an exported Markdown or JSON file for a 25-turn conversation completes in under 1 second.
- **SC-004**: Persistent storage read and write operations introduce 0 perceptible frame drops or typing delays during active streaming or composer interaction.
- **SC-005**: In private browsing mode or when storage access is denied, 100% of core chat features remain operational in session-only mode with zero unhandled errors.

---

## Assumptions

- Users access the web interface using modern evergreen browsers (Chrome, Firefox, Safari, Edge) with standard client-side storage capabilities (`localStorage` and/or `IndexedDB`).
- Client-side storage is partitioned per origin (`http://127.0.0.1:8080` / `http://localhost:8080`), ensuring complete isolation between browser domains.
- Cloud account sync and server-side database synchronization are out of scope for this feature; all persistence is local to the user's browser runtime.
- Multi-device sync is not required for this offline LLM setup; conversations belong to the client device accessing the container.
